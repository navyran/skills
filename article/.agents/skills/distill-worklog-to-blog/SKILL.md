# Distill Worklog To Blog

将原始工作记录转成面向读者的经验分享文章，而不是操作流水账或技术分析报告。先核实事实和脱敏，再写作和生图，最后校验并保存到日期目录。

## 默认约定

- 默认博客根目录：/Users/navin/Workspace/docs/blog。
- 默认日期：使用本地时区当天日期，格式为 YYYYMMDD；用户指定日期时以用户为准。
- 将 Markdown 和文章图片放在同一个日期目录，图片使用 ./filename.ext 相对链接。
- 在最终目录中直接创作，避免完成后移动文件造成链接失效。
- 不覆盖无关同名文章；若用户要求优化现有文章则原地更新，否则使用新的明确文件名。
- 不提交、不推送，除非用户明确要求。

## 工作流

### 0. 准备最终目录

先解析目标日期和博客根目录，得到 /Users/navin/Workspace/docs/blog/YYYYMMDD。只读检查目录中的现有文章和图片，再按需创建日期目录。

根据文章主题生成不含敏感信息的 Markdown 文件名；若发现同名文件，只有用户明确要求优化该文章时才原地更新，否则使用不同文件名。在此目录中直接创建文章和配图，不先写到业务仓库再移动。

### 1. 确定素材范围

优先使用当前对话中已经提供的完整记录，不重复要求用户说明。必要时只读检查用户指定的 Git 记录、日志、报告、方案和代码。

建立临时事实清单，区分：

- 已由记录或文件证明的事实。
- 可以合理解释但尚未证实的推断。
- 不应公开的业务和环境信息。
- 值得分享、能够迁移到其他场景的经验。

不得为了增强故事性虚构数据、故障、工具使用或结果。

### 2. 提炼文章主线

用一句话确定文章希望读者带走的核心观点，再选择 3–7 条支撑经验。优先讲决策方法、踩坑和可复用规则，弱化具体项目功能介绍。

写作前完整阅读 [文章结构](references/article-structure.md)。除非用户指定其他体裁，按照以下读者路径组织：

场景 → 痛点 → 抽象案例 → 方案 → 经验 → 工具技能 → 泛化 → 价值 → 落地

不要按聊天时间线逐条复述操作，不要将正文写成测试报告、故障分析单或产品说明书。

### 3. 先脱敏，再写作和生图

完整阅读 [脱敏规则](references/desensitization.md)，建立替换映射后再起草文章。

至少处理：

- 公司、产品、客户、人员和账号身份。
- 内部域名、IP、端口、路径、分支、容器和环境名。
- 真实接口、字段、数据库、队列、存储键和业务代码。
- 密码、令牌、密钥、Cookie、签名和权限信息。
- 订单、任务、账单、手机号、金额、余额和长数字标识。
- 云厂商、模型或供应商名称；除非它们是公开方法讨论的必要对象。

脱敏后仍需保留技术因果关系。不要只删除名词而让案例无法理解；使用“某内容处理平台”“异步任务服务”“测试环境”“业务记录标识”等等价角色替换。

不得把敏感信息写入图片提示词、文件名、图片文字、替代文本或元数据。

### 4. 写成经验分享文章

从 [博客模板](assets/blog-post-template.md) 选择需要的结构，不机械保留所有小节。

写作要求：

- 用一个具体但脱敏的场景开篇，让读者先理解为什么这件事重要。
- 将案例压缩成支持观点的证据，不展开真实业务细节。
- 将方案写成读者可以复用的做法，说明边界和失败条件。
- 将人工介入、操作异常和修正过程提炼为经验闭环。
- 说明方法可以迁移到哪些场景，也明确不适用范围。
- 用交付、质量、知识沉淀或风险控制说明价值。
- 结尾给出从最小场景开始的落地路径。

需要展示复杂流程、反馈闭环或多系统关系时，可以先用 Mermaid 或结构化文字梳理关系，但不得把 Mermaid 作为最终发布内容。文章主体完成后必须将全部流程图转换成图片。

### 5. 生成公开可用的配图并替换流程图

使用可用的图像生成 Skill 或工具制作封面和正文流程图；调用前确保提示词已经脱敏。

默认封面要求：

- 16:9 横版技术插图。
- 无公司标志、产品界面、真实人物和内部数据。
- 默认不在图片中生成文字，避免错字和品牌泄漏。
- 视觉概念围绕文章核心方法，而不是复刻具体业务页面。
- 将图片保存到文章同目录，使用稳定、无敏感信息的英文文件名。

完整阅读 [流程图图片化规范](references/diagram-rendering.md)。对文章中的每个 Mermaid 图分别调用图像生成能力，检查中文标签和流程方向后，将最终 PNG/WebP 保存到文章同目录，并用标准 Markdown 图片引用和简短图注替换原代码块。

只有复杂关系确实更容易通过图形理解时才增加正文配图，不为了装饰堆砌图片。最终文章不得残留 Mermaid 代码块。

### 6. 做五轮优化

1. **事实轮**：删除未验证结论，区分事实与推断。
2. **叙事轮**：检查是否遵循场景、痛点、案例、方案和价值的读者路径。
3. **脱敏轮**：进行语义检查和敏感关键词扫描，确认图片提示词也安全。
4. **视觉轮**：检查标题层级、表格、生成图片、代码围栏和本地图片链接，确认 Mermaid 已全部替换。
5. **价值轮**：删除只能描述项目、不能帮助其他读者的段落。

用户对结构、脱敏或表达提出修正时，先更新文章。如果反馈揭示了可复用规则，且用户要求更新本 Skill，再将规则写回对应参考资料。

### 7. 校验并交付

运行：

~~~bash
python3 ~/.codex/skills/distill-worklog-to-blog/scripts/validate_blog_post.py /absolute/path/to/article.md
~~~

对已知业务标识增加多个 --deny 参数。不要把密码、令牌或密钥原文放进命令行；此类信息使用模式扫描和人工语义检查。

校验失败时修复后重跑。交付前确认：

- Markdown 和所有本地图片均位于目标日期目录。
- 图片链接可解析。
- 文章没有占位符、未闭合代码块和尾随空格。
- 文章没有 Mermaid 代码块，所有流程图均已生成并替换为 PNG/WebP。
- 敏感信息扫描没有命中。
- 目标博客仓库的 Git 状态已读取但未擅自提交。

最终回复提供文章和图片的绝对可点击链接，概括文章主线、脱敏和校验结果，并说明是否尚未提交。
